# Data Model: SEO Optimization

**Feature**: 003-seo-optimization
**Date**: 2025-11-21
**Purpose**: Define data structures and entities for SEO implementation

---

## Overview

SEO optimization is a **read-heavy** feature that consumes existing data (hackathons, profiles) and transforms it into SEO-friendly formats. **No new database tables are required.** All entities are runtime data structures and configuration objects.

---

## Core Entities

### 1. PageMetadata

**Purpose**: Represents complete metadata for a single page

**Fields**:
```typescript
interface PageMetadata {
  title: string;                    // Page title (max 60 chars recommended)
  description: string;              // Meta description (max 160 chars)
  canonical: string;                // Canonical URL
  openGraph: {
    title: string;
    description: string;
    url: string;
    type: 'website' | 'article' | 'profile';
    images: string[];               // Array of OG image URLs
    siteName: string;
  };
  twitter: {
    card: 'summary' | 'summary_large_image';
    title: string;
    description: string;
    images: string[];
  };
  keywords?: string[];              // Optional keywords array
}
```

**Validation Rules**:
- `title`: 1-60 characters (SEO best practice)
- `description`: 1-160 characters (truncate if longer)
- `canonical`: Must be absolute URL with protocol
- `openGraph.images[0]`: Must be 1200x630px for optimal display
- `twitter.card`: Use 'summary_large_image' for pages with hero images

**State Transitions**: N/A (immutable once generated)

**Usage**: Generated by `generateMetadata()` in page components

### 2. SitemapEntry

**Purpose**: Represents a single URL in the sitemap

**Fields**:
```typescript
interface SitemapEntry {
  url: string;                      // Absolute URL
  lastModified: Date;               // Last update timestamp
  changeFrequency: 'always' | 'hourly' | 'daily' | 'weekly' | 'monthly' | 'yearly' | 'never';
  priority: number;                 // 0.0 to 1.0
}
```

**Validation Rules**:
- `url`: Must be absolute URL starting with baseUrl
- `lastModified`: Must be valid Date object
- `changeFrequency`: Must match Google Sitemap Protocol values
- `priority`: Must be between 0.0 and 1.0
- Total entries per sitemap file: Max 50,000 (Google limit)
- Total sitemap file size: Max 50MB uncompressed

**Grouping Strategy**:
```typescript
{
  static: SitemapEntry[];        // Landing, about, pricing, etc. (priority: 0.8-1.0)
  hackathons: SitemapEntry[];    // All hackathon pages (priority: 0.8, daily)
  profiles: SitemapEntry[];      // Public profiles (priority: 0.7, weekly)
  blog: SitemapEntry[];          // Blog posts (priority: 0.6, weekly)
  docs: SitemapEntry[];          // Documentation (priority: 0.7, monthly)
}
```

**State Transitions**: Regenerated on build or on-demand request

### 3. StructuredDataSchema

**Purpose**: Represents Schema.org JSON-LD data

**Base Interface**:
```typescript
interface BaseSchema {
  "@context": "https://schema.org";
  "@type": string;                  // Schema type (Organization, Event, Person, etc.)
}
```

**Concrete Schemas**:

#### 3a. OrganizationSchema
```typescript
interface OrganizationSchema extends BaseSchema {
  "@type": "Organization";
  name: string;                     // "StackPass"
  url: string;                      // Homepage URL
  logo: string;                     // Logo image URL
  description: string;              // Company description
  sameAs: string[];                 // Social profile URLs
  contactPoint?: {
    "@type": "ContactPoint";
    email: string;
    contactType: "customer service";
  };
}
```

**Usage**: Root layout and homepage

---

#### 3b. EventSchema
```typescript
interface EventSchema extends BaseSchema {
  "@type": "Event";
  name: string;                     // Hackathon title
  description: string;              // Hackathon description
  startDate: string;                // ISO 8601 format
  endDate: string;                  // ISO 8601 format
  eventStatus: "https://schema.org/EventScheduled" | "https://schema.org/EventCancelled";
  eventAttendanceMode: "https://schema.org/OnlineEventAttendanceMode";
  location: {
    "@type": "VirtualLocation";
    url: string;                    // Hackathon detail page URL
  };
  organizer: {
    "@type": "Organization";
    name: "StackPass";
    url: string;
  };
  offers?: {
    "@type": "Offer";
    price: string;                  // "0" for free
    priceCurrency: string;          // "USD"
    availability: "https://schema.org/InStock";
  };
  image?: string;                   // Hackathon image URL
}
```

**Validation Rules** (FR-012):
- `startDate`/`endDate`: Must be valid ISO 8601 strings
- `eventStatus`: Use EventScheduled for active/upcoming, EventCancelled if cancelled
- `eventAttendanceMode`: Always OnlineEventAttendanceMode (virtual hackathons)
- `location.url`: Must be absolute URL to hackathon page
- `offers.price`: Use "0" for free events, prize amount for paid

**Usage**: Hackathon detail pages (`/hackathons/[slug]`)

---

#### 3c. PersonSchema
```typescript
interface PersonSchema extends BaseSchema {
  "@type": "Person";
  name: string;                     // User's display name
  image: string;                    // Avatar URL
  url: string;                      // Profile page URL
  description?: string;             // User bio
  jobTitle?: string;                // Optional job title
  sameAs?: string[];                // GitHub, LinkedIn, Twitter URLs
}
```

**Validation Rules** (FR-013):
- `name`: Required, use `display_name` from devcard or fallback to GitHub username
- `image`: Required, use `avatar_url` from devcard
- `description`: Optional, use `custom_bio` if available
- `sameAs`: Include GitHub profile and any social_links from devcard

**Usage**: User profile pages (`/[username]`)

#### 3d. BreadcrumbListSchema
```typescript
interface BreadcrumbListSchema extends BaseSchema {
  "@type": "BreadcrumbList";
  itemListElement: BreadcrumbItem[];
}

interface BreadcrumbItem {
  "@type": "ListItem";
  position: number;                 // 1-indexed
  name: string;                     // Breadcrumb label
  item: string;                     // Absolute URL
}
```

**Validation Rules** (FR-014):
- `position`: Must start at 1 and increment sequentially
- `name`: Clear, human-readable labels (e.g., "Home", "Hackathons", "Hackathon Title")
- `item`: Absolute URLs, last item should match current page URL

**Usage**: All pages with breadcrumb navigation

### 4. OGImageConfig

**Purpose**: Configuration for generating dynamic Open Graph images

**Fields**:
```typescript
interface OGImageConfig {
  type: 'hackathon' | 'profile' | 'generic';
  params: HackathonOGParams | ProfileOGParams | GenericOGParams;
}

interface HackathonOGParams {
  title: string;                    // Hackathon title (max 60 chars for display)
  prize: number;                    // First prize amount
  currency: string;                 // "USD", "EUR", etc.
  startDate?: string;               // Optional display date
}

interface ProfileOGParams {
  name: string;                     // User display name
  bio?: string;                     // Short bio (max 100 chars)
  avatarUrl: string;                // User avatar
  techStack?: string[];             // Top 5 tech skills
}

interface GenericOGParams {
  title: string;
  subtitle?: string;
  logo?: boolean;                   // Include StackPass logo
}
```

**Validation Rules** (FR-008, FR-009, FR-010):
- Output dimensions: 1200x630px (required)
- File size: <5MB (constraint)
- Fallback: Use `/images/og.png` if generation fails

**Usage**: API routes at `/api/og/[type]` generate images, metadata references them

### 5. RobotsConfig

**Purpose**: Configuration for robots.txt generation

**Fields**:
```typescript
interface RobotsConfig {
  rules: RobotsRule[];
  sitemap: string;                  // Sitemap URL
  host?: string;                    // Optional preferred host
}

interface RobotsRule {
  userAgent: string;                // '*', 'Googlebot', etc.
  allow?: string[];                 // Allowed paths
  disallow?: string[];              // Disallowed paths
  crawlDelay?: number;              // Optional delay in seconds
}
```

**Validation Rules** (FR-025, FR-026, FR-027):
- `disallow`: Must include ['/app/', '/api/', '/admin/', '/super-admin/']
- `allow`: ['/'] for public access
- `sitemap`: Must be absolute URL to sitemap.xml

**Usage**: Generated by `src/app/robots.ts`

## Derived Data

### SitemapGroups

**Purpose**: Organize sitemap entries by content type for efficient generation

```typescript
interface SitemapGroups {
  static: {
    entries: SitemapEntry[];
    count: number;
    priority: 0.8 - 1.0;
    frequency: 'monthly';
  };
  hackathons: {
    entries: SitemapEntry[];
    count: number;
    priority: 0.8;
    frequency: 'daily';
  };
  profiles: {
    entries: SitemapEntry[];
    count: number;
    priority: 0.7;
    frequency: 'weekly';
  };
  blog: {
    entries: SitemapEntry[];
    count: number;
    priority: 0.6;
    frequency: 'weekly';
  };
  docs: {
    entries: SitemapEntry[];
    count: number;
    priority: 0.7;
    frequency: 'monthly';
  };
}
```

**Generation Logic**:
1. Fetch all content (hackathons, profiles, blog posts, docs)
2. Filter (only public profiles, only active/completed hackathons)
3. Group by type
4. Check total count: if > 50,000, split into sitemap index
5. Sort by priority and lastModified

## Data Flow

### Metadata Generation Flow
```
Page Request
→ generateMetadata() function
→ Fetch data (hackathon/profile)
→ Generate PageMetadata
→ Return to Next.js
→ Render in <head>
```

### Sitemap Generation Flow
```
/sitemap.xml Request
→ Query database (hackathons, profiles, blog, docs)
→ Filter public/active content
→ Transform to SitemapEntry[]
→ Check count < 50K
→ Return MetadataRoute.Sitemap
→ Next.js renders XML
```

### Structured Data Flow
```
Page Component
→ Fetch data
→ Build Schema object (Event/Person/etc.)
→ Pass to <StructuredData> component
→ Render <script type="application/ld+json">
→ Included in page HTML
```

### OG Image Flow
```
Metadata references /api/og/hackathon?title=X&prize=Y
→ Social platform requests image
→ API route handles request
→ Generate ImageResponse (1200x630)
→ Vercel caches image
→ Return to social platform
```

## Query Requirements

### Sitemap Queries
```sql
-- Hackathons for sitemap (FR-016)
SELECT id, slug, updated_at
FROM hackathons
WHERE status IN ('active', 'voting', 'completed');

-- Public profiles for sitemap (FR-017)
SELECT url_slug, updated_at
FROM devcards
WHERE is_public = true;

-- Blog posts (existing query)
-- Documentation pages (existing query from fumadocs)
```

**Performance Target**: All queries combined < 3 seconds (constraint)

### Metadata Queries
```sql
-- Single hackathon
SELECT id, slug, title, description, start_at, submission_deadline_at, prizes, updated_at
FROM hackathons
WHERE slug = $1;

-- Single profile
SELECT url_slug, display_name, custom_bio, avatar_url, social_links, updated_at
FROM devcards
WHERE url_slug = $1 AND is_public = true;
```

**Performance Target**: <200ms per query (existing ISR caching helps)

## Storage Considerations

**No New Database Tables**: All SEO data is derived from existing tables:
- `hackathons`: Source for Event schema, sitemap, metadata
- `devcards`: Source for Person schema, sitemap, metadata
- Existing blog/docs infrastructure

**Caching Strategy**:
- Metadata: Generated at request time, cached by Next.js ISR (existing: 60s-600s)
- Sitemap: Generated at build time or on-demand (no explicit cache needed, Next.js handles)
- OG Images: Cached by Vercel Edge (automatic)
- Structured Data: Generated on-the-fly (minimal overhead, pure JS transformation)

**No Additional Storage Required**: SEO implementation is purely read-transform-render.
